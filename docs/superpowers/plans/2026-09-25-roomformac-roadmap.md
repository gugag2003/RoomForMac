## Decisions made while planning (confirm with the product owner)

Research into Mole V1.56.0 for Plan 1 surfaced four places where the spec's wording cannot be met as written. The plans implement the closest safe behaviour:

1. **Uninstaller leftovers are listed, not individually deselectable (v1).** Mole's uninstall performs app-level side effects that cannot be scoped per file (Homebrew `--zap`, `defaults` domain deletion, launch-agent unloading, ByHost plists discovered at removal time). v1 selects per app and shows every leftover with its size before confirmation (spec §5.2 said "checkboxes").
2. **Smart Clean offers only path-based items (v1).** Cleanups that run a tool instead of deleting a previewed path — Homebrew cleanup/autoremove, npm/pip/uv/corepack/conda/bun/Go tool caches, stopping leaked automation browsers — have no per-path preview, so they cannot honour an exact selection. The engine skips them whenever a selection is active. Unavailable iOS simulators *are* offered: they are deleted one by one through `simctl`.
3. **No administrator access until Plan 7.** Mole asks for passwords with its own "Mole"-titled AppleScript dialog. Until spike S3 picks a native mechanism, the engine runs with `MOLE_NO_AUTH=1` plus a failing `sudo` shim, so system-level items do not appear. Items that would need a password are tagged "Needs your password" and never sent (Plan 3 Ruling 11): in Smart Clean, Time Machine items and items in folders you cannot write; in the Uninstaller, Homebrew casks and apps in a folder you cannot write. For a standard user that is every app in `/Applications`; for an administrator, a root-owned app there is removable.
4. **Real-output parser coverage comes from the engine integration suite** that CI runs on every push against the freshly built engine, instead of checked-in recorded fixtures (spec §13). Unit tests use exact inline samples of the protocol.

## Spec errata (listed, not yet edited into the spec)

Where the built software differs from the spec, the plans' Rulings decide. The differences are collected here until one errata pass edits the spec.

**Found by Plan 3** (`2026-09-27-plan-3-features.md`):

1. **§4.3, patch flags and fields.** The patches are `0001`–`0006` in `patches/mole/`, and `docs/engine-protocol.md` is the contract.
   - Clean events (0002) go to the file named by `MOLE_JSON_EVENTS_FILE`, not to stdout: `section`, `candidate`, `item` (with `size_kb`, `size_known`, `count` and `covered_by`), `result` (with `action`, `detail` and, since patch 0006, `size_kb` on `removed`) and `summary`. The spec's `size_bytes`, `needs_admin`, `note`, `progress`, `status`, `bytes` and `reason` do not exist.
   - `--only-list <file>` is `MOLE_SELECTION_FILE` (0003). The uninstall flags are `MOLE_UNINSTALL_APP_PATHS_FILE`, `MOLE_UNINSTALL_PREVIEW_ONLY` and `MOLE_ASSUME_YES` (0004). A preview lists every leftover with its size (`leftover_items`, added when Plan 3 amended 0004), and a real run reports one `app_result` per app, not a `result` per item.
   - `analyze-go --trash-list FILE` (0005) writes its events on stdout and takes no `--json`.
   - P4 (b), the native password path, waits for Plan 7.
   - Status does not use `status --json`: it runs `status-go --watch`, with no patch (item 2).
2. **§4.4, Status cadence.** The spec says "`status --json` every 2 s while any status UI is visible, 10 s when only the menu bar is open, paused otherwise". Built: one `status-go --watch --interval 2s` at a time, shared by the window and the menu bar, and paused and resumed with `SIGSTOP` and `SIGCONT`. It is live while the Status section is on screen or the menu-bar panel is open, and **paused while only the menu-bar extra shows with its panel closed**, instead of polling every 10 s. That is Plan 3 Ruling 16 as the controller revised it on 2026-09-27 (Plan 2's execution ruling E17): the extra's label shows no live numbers, a resumed process answers within about 0.5 s of the panel opening, and the pause saves about 3% of a core all day. After 5 minutes paused, the process ends. *If wrong:* map `menuBarInserted` to `.background` in `StatusCadence.resolve`, one line; `StatusMonitor` still supports the 10 s cadence.
3. **§4.6, names in the data flow.** `CleanScanModel` is `SmartCleanModel`. `AllowanceGate.check(selection) → ok | exceedsRemaining | exhausted` is `RemovalGate.check(RemovalRequest) → .allow | .exceedsRemaining(remainingBytes:) | .exhausted`, called when **Clean** is pressed, before the confirmation sheet, and by the Uninstaller before any app is quit. `AllowanceLedger.record(removed bytes only)` is `RemovalRecorder.record(RemovalConfirmation)`: one path-free confirmation per removal, as it arrives, keyed by run and sequence. `Telemetry: cleanup_succeeded` goes through `RunReporter.cleanupFinished(CleanupReport)`. The engine commands are `bin/clean.sh --dry-run` and `bin/clean.sh` with `MOLE_SELECTION_FILE` (item 1). Plan 3 ships `UnlimitedRemovalGate` and `NoOpRemovalRecorder`, and Plan 5 plugs in the allowance.
4. **§5.2, leftover checkboxes.** The drawer lists every leftover with its size, grouped by kind, but leftovers cannot be deselected one by one: selection is per app (roadmap decision 1; Plan 3 Ruling 15). Progress is per app ("Moving <name> to the Trash"), not per item, and the summary's hint is "Empty the Trash to free up this space." with **Open Trash**; there is no Empty Trash button.
5. **§6, the Finder reason.** Row 3 gives Finder's reason as "Trash moves", as if Finder moved what RoomForMac removes. The engine moves items to the Trash itself (a direct move, a batched rename, then `/usr/bin/trash`) and asks Finder only when that fails. Status never talks to Finder: `status-go` runs with the `status-bin/osascript` stub, and the app reads free space itself. The Finder card and `NSAppleEventsUsageDescription` say so ("Moves apps to the Trash if the usual way fails"; Plan 2 Ruling 10 and E14). Row 4's reason for System Events ("running-app list") is also incomplete: the engine removes an uninstalled app's login items through System Events too.
6. **Notification triggers (§5.6 and §6 row 6).** The spec asks for the Notifications permission but names no trigger. Built (Plan 3 Ruling 20): RoomForMac posts a notification only when **Notify me when a scan or cleanup finishes** is on, the permission is granted and RoomForMac is not the active app, and only when a Smart Clean scan finishes, a Smart Clean cleanup ends (however it ends) or an uninstall ends. The text carries counts and sizes, never a name, and a click opens the matching section. There are no low-space or scheduled notifications in v1.

**Found by Plan 6** (`2026-09-29-plan-6-distribution.md`):

1. **§12, Signing: hardened runtime.** The spec says "hardened runtime off (not required without notarization)". Built (Ruling 5): on in Release (`ENABLE_HARDENED_RUNTIME[config=Release] = YES`), off in Debug. It makes the app ignore `DYLD_*` injection under RoomForMac's Full Disk Access and Automation grants. The entitlements are exactly `com.apple.security.automation.apple-events`, which the runtime makes necessary, and `com.apple.security.cs.disable-library-validation`, because a self-signed certificate has no Team ID and library validation would refuse Sparkle. This settles the security item Plan 2's E16 carried forward. *If wrong:* turn the runtime off for Release, drop the two entitlements and flip `RFM_EXPECT_HARDENED` in `check-release-app.sh` (Ruling 5's fallback).
2. **§12, Updates: where the feed lives.** The spec says "EdDSA-signed appcast hosted on GitHub Releases/Pages". Built (Rulings 2 and 3): the feed and the appcast are release assets, read through `https://github.com/gugag2003/RoomForMac/releases/latest/download/appcast.xml` (`RFM_FEED_URL`, fixed for life), and each release adds one item to the previous release's appcast. Pages carries only the site. Once a custom domain is set, `github.io/<repo>` answers `301` to `http://`, which App Transport Security refuses, so a feed on Pages would die the day a domain was added.
3. **§12, Release: what a release publishes.** The spec says "tag → build universal app → sign → DMG → Sparkle appcast → GitHub Release; appends that release's token fixture". Built (Rulings 4, 11, 12 and 13): `release.yml` runs `build`, `publish`, `pages` and `fixture`. A release has six assets: the DMG for people; `RoomForMac-X.Y.Z.tar.xz`, the update archive Sparkle reads (Sparkle mounts a DMG update with `hdiutil`, which macOS 27 deprecates); a `-source.tar.gz` that carries `vendor/mole`, for the GPL's Corresponding Source; `appcast.xml`; `latest.json`; and `SHA256SUMS`. They go to a draft release, which is then published as the latest, and the live feed is checked. The token fixture is one optional hook, `scripts/release-hooks/token-fixture`, which is skipped with a notice until Plan 5 supplies it and adds `--required`.
4. **§12, Signing (and §3.3): where the private key lives.** The spec says "private key in GitHub Actions secrets" (§3.3: "kept in CI secrets"). Built (Ruling 14): the environment `release` holds `RFM_SIGNING_P12_BASE64`, `RFM_SIGNING_P12_PASSWORD` and `SPARKLE_ED_PRIVATE_KEY`. It requires the owner's approval, and only the `build` job of `release.yml` names it. There are no repository-level secrets.
5. **§16, the price check.** The spec says "the release workflow fails if the price is unset". Plan 6 has no price: the check is Plan 5's own step in `release.yml`, added when the price exists, next to the `--required` flag on the fixture hook (Ruling 12).
6. **§4.1, script names.** `sign.sh` and `release.sh` do not exist. The scripts are `import-signing-identity.sh`, `make-signing-identity.sh`, `prepare-sparkle.sh`, `make-update-keys.sh`, `check-release-app.sh`, `make-dmg.sh`, `make-update-archive.sh`, `make-source-archive.sh`, `make-appcast.sh`, `release-summary.sh`, `release-preflight.sh`, `release-hook.sh`, `stage-site.sh` and `rehearse-update.sh`. `.github/workflows/` holds `ci.yml`, `release.yml` and `pages.yml`. `site/` holds the download, Open Anyway, thanks and privacy pages and a 404 page.
7. **§3.3, the Open Anyway guide.** Unchanged in substance: it lives on the site (`site/open-anyway/`, with CSS mock dialogs whose button pulses, and a static outline under Reduce Motion) and as the DMG window's background (`packaging/dmg/`). The DMG background is a still image, not an animation.
